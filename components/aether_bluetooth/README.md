# Classic Bluetooth audio output and HID

The ESP-IDF 6.1 Bluedroid service manages two roles on the same Classic Bluetooth controller. Bluetooth starts off. The first explicit radio-on request creates the owner task, with a 6 KiB internal stack for operations that can reach NVS or ROM. NVS must already be initialized, and Bluedroid stores bond information there.

| Settings path | Connection and lifetime |
| --- | --- |
| 蓝牙 → 音频输出 | A2DP Source discovers and connects to the selected headphones or speaker. Disconnecting there ends only the audio link. |
| 蓝牙 → 蓝牙键鼠 | HID Device accepts a connection from a compatible host during pairing. The device prompts for confirmation and remembers the approved host in NVS. While HID stays enabled, it can reconnect to that host after an unexpected link loss. |
| 电脑键鼠 → 无线键盘 / 飞鼠 / OBS | All three modes use the same HID link. Leaving the page stops motion sampling and releases pending keys and mouse buttons while keeping the host connected. |

Back navigation and the long-press exit leave Wi-Fi and both Bluetooth links running. **关闭键鼠** stops only HID, leaving requested audio enabled. **关闭全部蓝牙** and system shutdown request teardown of both Bluetooth roles. Closing the audio settings page leaves its connection running.

The configuration enables `BT_ENABLED`, `BT_BLUEDROID_ENABLED`, `BT_CLASSIC_ENABLED`, `BT_A2DP_ENABLE` and `BTDM_CTRL_MODE_BR_EDR_ONLY`. HID Device is enabled for AC101S. The controller uses the SDK default two ACL slots. A2DP and AVRCP for one peer share an ACL, and the HID host can use the other. Audio output initiates its own connections. The HID service controls the inbound discovery and reconnection windows and defers starting them while Bluetooth audio is discovering or connecting.

All radio commands are asynchronous. Call `get_status()` for state, completion errors and snapshots, `get_device()` for discovered addresses/names, and `poll_remote()` from the app audio service. Scan results are capped at 16; audio devices can replace a non-audio entry when full. CoD is an indication, not proof of A2DP support: a selected non-headphone can fail connection. Modern Just Works pairing and a legacy `0000` headphone PIN are supported; numeric comparison is accepted only for the selected connecting peer. Headphones requiring another manually entered PIN or a 16-digit PIN need a future entry flow. Authentication failures remain visible rather than being called file/media errors.

Connection diagnostics log SDK queue acceptance separately from success, internal DMA heap before connection, GAP ACL completion/disconnection status and handle, authentication status, selected-peer PIN/SSP reply acceptance/results, A2DP state and negotiated codec masks. PINs, passkeys and link keys are not logged. Status exposes `connection_attempts` and raw `auth_status`, `acl_status`, `acl_disconnect_reason`, `a2dp_disconnect_reason` (`-1` means no event observed during this attempt). These raw values are SDK/HCI values, not `esp_err_t`; a failed OPEN can be reported by the SDK as A2DP DISCONNECTED/NORMAL, so an unfinished connection still retains a failure in `last_error`. No bonds are automatically deleted, and no connection retry is automatic.

The connection deadline is 20 seconds. Cancellation sets DISCONNECTING before invoking the SDK so a fast callback cannot be overwritten. A rejected disconnect on an established connection retains its error and permits manual retry. A rejected cancellation of a pending connect retains ownership in DISCONNECTING: new connects, scans and audio starts remain blocked, including after late CONNECTED/configuration callbacks. If cancellation never completes within three seconds, profiles/host are closed before another attempt is permitted; the radio becomes off and the user explicitly re-enables it. Direct radio-off also waits for disconnection at most once before continuing legal profile/host teardown, rather than resetting a cancellation deadline on every cleanup retry. Resources remain allocated until teardown completes. The initialized controller is retained, preserving S31's once-init constraint.

`get_sink()` returns the external transport for the audio driver. Input is 48kHz PCM16 stereo. Actual `ESP_A2D_AUDIO_CFG_EVT` SBC settings choose 48k/44.1k output and mono/stereo; unsupported rates/codec settings are explicitly rejected. Conversion retains rational phase and the previous sample across caller chunks. The 48k path copies samples directly. Negotiated mono is downmixed from stereo. The 8,192-frame PSRAM FIFO provides normal producer backpressure to music/NES/MP4 instead of dropping PCM or letting emulation run faster than its audio clock. Writes have a bounded deadline (maximum 3 seconds), wait in short increments, and are canceled by stop, disconnect, reconfiguration or radio-off. A partially written failed stream is invalidated and must be restarted, so a caller cannot accidentally retry duplicated audio.

Source-side codec configuration is an actual IDF6.1 path: `btc_av.c`'s `bte_av_media_source_callback()` receives `BTA_AV_MEDIA_CFG_EVT`, posts `BTC_AV_CONFIG_EVT`, and the opening/opened state handlers report `ESP_A2D_AUDIO_CFG_EVT`. `btc_a2dp_source.c` derives PCM feeding rate from the negotiated encoder configuration. Host fixtures model these events; they do not by themselves prove real headset negotiation.

The A2DP pull callback never waits for a mutex/semaphore, allocates memory or invokes the codec/player/UI. It reads FIFO under short critical sections, fills shortages with zero and records underruns. Application writes are serialized separately. AVRCP host callbacks enqueue play/pause/stop/next/previous and volume-key actions; the app audio service applies them outside the Bluetooth stack. Software PCM master volume is authoritative; the same value is not sent to the headphone as an extra hardware attenuation. Incoming absolute-volume notifications update `status.peer_volume` only. The peer's own hardware volume remains independent.

Radio-off stops discovery/connections, waits for asynchronous profile deinitialization, disables/deinitializes Bluedroid, disables the controller, then frees the PCM FIFO after the producer leaves. Failed/late teardown retains resources for retry. The ESP32-S31 IDF6.1 [`esp_bt.h`](https://github.com/espressif/esp-idf/blob/master/components/bt/include/esp32s31/include/esp_bt.h) explicitly states controller initialization/deinitialization may happen only once and reinitialization after controller deinit is unsupported. For repeatable user on/off, the initialized but disabled controller context is therefore retained. `del()` is terminal cleanup after the audio sink has been detached; it deinitializes the controller and future creation is rejected. No `esp_bt_mem_release`/`esp_bt_controller_mem_release` call exists here.

See [host tests](../../tests/bluetooth_runtime/README.md). Headphone interoperability, RF coexistence with Wi-Fi, actual SBC/BT task CPU/stack use, end-to-end latency and sustained S31 playback still require device acceptance. FIFO/transport counts are not proof of audible output or lip sync.
