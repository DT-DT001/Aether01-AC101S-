# Aether01 USB TF-card disk

ESP32-S31, existing ESP-IDF6.1, pinned `espressif/esp_tinyusb`2.3.0. Initialization is lazy and defaults OFF on every boot. Only the settings switch requests entry; no persisted ON state or automatic USB attachment takeover is used.

## USB speed release: flashed, throughput not yet measured

The user initially requested an unflashed candidate, then authorized the update. The final 16KiB release is now installed on COM36. All three flash hashes and matching-ELF `106a371d5` boot pass, including 64MiB flash, the 32MiB PSRAM@200MHz XIP self-test, 14 apps, TF mount and panel/touch/QMI/DPS/RTC startup. TE is around 59.70–59.74Hz; see the local [deployment record](../../build/usb-speed16-com36-manifest.json). The final 16KiB [build passes with the existing ESP-IDF6.1 environment](../../tmp/usb-speed16-final-build.log). Fixed artifacts remain in `build/releases/usb-speed16-candidate/`; see the [build manifest](../../build/usb-speed16-candidate-manifest.json). The user previously reported about 1.2MB/s writes, and a pre-update read-only [Windows hub query](../../tmp/usb-link-speed.json) confirmed High-Speed 480Mb/s. The new log tail only shows raw USB initialization starting; completed export, new throughput, sustained CRC/integrity and radio-memory behavior remain unverified. Local `build/` and `tmp/` evidence is not part of the source repository.

The final TinyUSB MSC transfer buffer is16KiB, enlarged from4KiB. Generated config and ELF `_mscd_epbuf` both confirm16,384 bytes; total ELF internal RAM grows by12,288 bytes and IRAM is unchanged. The sole effective sdkconfig change is the MSC buffer;255 production source hashes match across the build and the upstream default `tinyusb_msc.c.obj` remains excluded. The4KiB SD bounce buffer is unchanged. Direct DMA-safe, host-aligned access can issue a single16KiB/32-sector SD command; partial sectors and unsuitable buffers retain bounce/read-modify-write handling. Synchronous SD completion still precedes USB write acknowledgment.

Only raw USB card initialization attempts40/32/25/20MHz. Only card-init failure advances the ladder after full host/card cleanup and20ms powered off. Power/host/slot/cleanup faults abort with ownership retained; running write failures never trigger automatic replay or reclocking. Normal FatFS stays20MHz. Actual clock comes from SDK `real_freq_khz`; it can differ from the requested ceiling. Card VDD and pull-ups remain on shared BLDO1/VDD_SD3.3V. The100/200MHz UHS modes require1.8V and are not enabled; see the [official S31 SDMMC guide](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s31/api-reference/peripherals/sdmmc_host.html).

The USB page reads cached negotiated HS/FS/unknown, actual SD clock and fallback state without issuing synchronous USB/SD queries. Safe-eject, callback drain, sync acknowledgment, local-access gates and GPIO51 download-route restoration remain unchanged. [MSC/link](../../tmp/usb-speed-link-host.log), [storage](../../tmp/usb-storage-speed-host.log), [IO](../../tmp/usb-speed-io-host.log) and [real-LVGL UI](../../tmp/usb-speed-ui-host.log) host regressions pass. Hardware throughput, CRC behavior and sustained integrity are still untested for this candidate.

The application first blocks new TF requests and stops recorder/music/video/NES from its IO worker. Storage then rejects new leases, waits for all existing FILE/DIR users, fully unmounts FatFS and destroys its SD host. A fresh raw SD descriptor/host is created on the schematic pins with the existing BLDO1 supply policy. Raw USB access is bounded and serialized against card removal. DMA-safe, host-aligned buffers can transfer directly in SD multi-block commands up to16KiB. Other buffers retain the existing64-byte-aligned4KiB internal SD DMA bounce buffer; partial sectors use read/modify/write. No format operation is issued.

This component supplies the TinyUSB MSC callbacks, including synchronous WRITE10, SCSI SYNCHRONIZE CACHE and safe-eject handling. PREVENT/ALLOW is handled by the current TinyUSB `tud_msc_prevent_allow_medium_removal_cb()` built-in-command callback; it is not dispatched to the custom SCSI callback. ALLOW or STOP without LOEJ does not establish that the host safely ejected. A write is acknowledged only after the SD operation succeeds. The component deliberately does not call the wrapper's default MSC storage driver, which defers writes after acknowledging them. The wrapper's two internal mount-policy hooks are satisfied by no-op functions in the same object as the entry point. With the pinned 2.3.0 archive, its `tinyusb_msc.c.obj` must stay out of the final link; verify the linker map after any dependency change. Upstream managed sources are not edited.

While a configured host still has the card, the user must eject it on the PC before disabling the switch. The normal `aether_usb_msc_exit()` remains strict when no host eject or reliable physical absence has been observed. Some host safe-removal paths do not provide a usable LOEJ notification. Only after the user explicitly confirms that the computer has safely removed the disk may the application call `aether_usb_msc_exit_confirmed()`. That confirmation bypasses the ownership check for this one call; it does not set `host_ejected`, persist an acknowledgment, or authorize a later USB session. Both exit paths stop new callbacks, drain existing SD operations, synchronize the card, disconnect/uninstall USB and only then release raw ownership and restore FatFS. Timeout or failed teardown retains the local gate.

A board VBUS callback can distinguish actual cable removal from a temporary USB bus reset; it is called only from the IO worker, never the GUI status query. The application may supply a board query, but TG29 VBUSGOOD=0 alone must be treated as unknown, not as physical absence. Suspend, reset and an idle bus do not imply safe removal. Physical TF-card removal refuses further USB IO; reinsertion requires explicitly leaving/re-entering export rather than silently presenting a different card under an old host mount.

On this board GPIO51 LOW is the measured working reset/download route. MSC selects HIGH before installing the USB driver and restores LOW only after complete uninstall or startup rollback; a live host is never automatically cycled between routes. The old schematic net labels conflict with the observed download route and are not treated as proof of the fitted-board mux polarity. ESP32-S31 OTG is HS-only UTMI; it is not ESP32-S3's assignable FS PHY. The component leaves USJ pad registers untouched and delegates UTMI setup/teardown to the official TinyUSB/IDF driver. Do not call `usb_new_phy(SERIAL_JTAG, INT)` on S31.

The fitted board has enumerated successfully on Windows with route HIGH as `AETHER01 TF Card Reader` / USBSTOR, presenting drive E: with capacity 7,939,817,472 bytes. In that hardware test, Windows later removed the drive and disk device node while the USB parent remained present; firmware did not observe a usable eject notification, so the earlier strict exit continued asking for safe removal. The single-call confirmed exit, current PREVENT/ALLOW callback and MAC correction described here have passed host regression only. Their on-device exit, final copy-integrity, card/cable-removal, shutdown and COM restoration acceptance must be recorded separately; enumeration alone does not establish those results.

The USB serial number reads `esp_read_mac(mac, ESP_MAC_EFUSE_FACTORY)` into a six-byte buffer. On ESP32-S31 the default-MAC API `esp_efuse_mac_get_default()` instead expands the result to an eight-byte EUI-64; it must not be called with that buffer. The serial remains twelve hexadecimal factory-MAC digits, with a valid all-zero fallback if the read fails.

Host tests: `sh tests/usb_msc/run.sh` and `sh tests/storage/run.sh`. They do not emulate USB electrical signaling, DWC DMA/cache behavior, Windows caching or SD electrical failure modes.

Cached diagnostic_stage values:0 idle,1 storage handover,2 routing,3 TinyUSB installation,4 waiting for host,5 configured host,6 ejected,7 callback drain,8 USB uninstall,9 local TF restore,10 off. Startup failure retains its originating stage even if rollback succeeds. These values remain available to the settings UI after serial output is unavailable.
